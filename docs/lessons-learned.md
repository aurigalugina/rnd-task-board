## Verdict & Sign-off

**Bug ketemu & diperbaiki 2026-08-20 — verdict big task yang SUDAH signed ikut berubah jadi "lose" belakangan, padahal sudah win saat sign-off.** `computeVerdict` awalnya selalu bandingin `deadline vs now()` walau task-nya sudah signed — jadi big task yang di-sign-off ON TIME (sebelum deadline) bisa balik jadi "lose" begitu waktu berjalan lewat deadline-nya (dibaca ulang di tanggal lain), padahal keputusan win/lose semestinya BEKU begitu sign-off terjadi (computed-at-read tidak berarti "hasil boleh berubah retroaktif setelah titik keputusan sudah lewat"). Fix: signature `computeVerdict(deadline, signedAt *time.Time, now)` — kalau `signedAt != nil`, bandingin `deadline vs signedAt` (BEKU selamanya, bukan `now`); kalau belum signed, baru bandingin `deadline vs now` (bisa lose kalau deadline lewat). `ListByBoard`/`loadBigTask` diubah utk pass `signedAt` (bukan `bt.Signed` boolean) ke fungsi ini. Ada regression test eksplisit di `handler_test.go` ("signed on-time di masa lalu, dibaca lama setelah deadline lewat" harus tetap "win"). Detail: `docs/decision-log/decision-log-verdict-backfill-signoff-20260820.md`.

**Backdate sign-off + edit Big Task (2026-08-20, super_user only) — kenapa fitur ini dibutuhkan.** Kebutuhan aslinya: sign-off data historis/hasil import yang salah kena "lose" karena tanggal sign-off aktual sudah lewat deadline. `PATCH /big-tasks/{id}/sign-off` menerima body opsional `{signed_at: "YYYY-MM-DD"}`, hanya super_user, divalidasi (tidak boleh masa depan, tidak boleh sebelum `start_date`, tidak boleh sebelum tanggal `day_entries` terakhir). Field audit `big_task_signoffs.signed_at_backdated_by` dipakai frontend untuk indikator "(backdated)" pada badge verdict — sengaja bukan kolom boolean, mengikuti pola `*_backdated_by`/`updated_by` (nullable FK ke `users`) yang dipakai untuk semua kebutuhan "siapa yang override" alih-alih tabel audit log terpisah.

**Bug ketemu & diperbaiki 2026-08-20 — endpoint `GET /notifications` 500 di SEMUA environment.** `backend/internal/notification/checker.go: computeAlertsForUser` referensi `bt.signed` — kolom itu TIDAK PERNAH ADA di tabel `big_tasks` (sign-off itu existence-pattern via tabel `big_task_signoffs`), jadi query selalu gagal `column bt.signed does not exist` sejak migration `0019`, luput dari testing manual karena badge notifikasi cuma nongol kalau ada alert. Ada bug KEDUA yang ketutup sama bug pertama (baru kelihatan setelah bug pertama di-fix, karena Postgres berhenti di error pertama): `EXTRACT(EPOCH FROM (bts.deadline - bts.start_date))` — `deadline`/`start_date` sama-sama tipe `date`, jadi `date - date` di Postgres SUDAH integer (jumlah hari), bukan `interval`, sehingga `EXTRACT(EPOCH FROM <integer>)` invalid. Fix: (1) filter unsigned diganti `NOT EXISTS (SELECT 1 FROM big_task_signoffs ...)`, (2) hilangkan `EXTRACT(EPOCH FROM ...)`, langsung pakai integer hasil `date - date`. Sekalian diekstrak fungsi murni `classifyAlert(actualPct, daysLeft int, s UserSettings)` (prioritas sign_off_ready > verdict_lose > deadline_soon) + test — sebelumnya inline di loop scan row, tidak testable.

## Day Entry & Progress

**Generate Daily Task → Day Entry**: membuat Daily Task insert satu baris `day_entries` per tanggal kalender dalam rentang `[start_date, end_date]` inklusif, dalam satu transaksi (SRS FR-DLY-01/02). `is_weekend` dihitung dari `entry_date` saat baca, tidak pernah disimpan.

**Day Entry bisa ditambah/dihapus manual (2026-08-10) — kenapa constraint dicabut.** Sebelumnya dibatasi satu baris per tanggal via `UNIQUE (daily_task_id, entry_date)`; constraint ini DICABUT (migration `0010`) karena user perlu breakdown lebih dari satu task di hari yang sama, dan perlu menghapus baris weekend/"lembur" yang ke-generate otomatis tapi PIC tidak mau lembur. `day_entries` di-`ORDER BY entry_date, created_at` (kolom `created_at` baru ditambah migration `0010`) — SENGAJA bukan `updated_at`, karena `updated_at` berubah tiap PATCH dan akan bikin urutan lompat kalau dipakai buat sorting. Detail: `docs/decision-log/decision-log-day-entry-add-delete-20260810.md`.

**Day Entry status jadi 3-state granular (2026-08-10, migration `0011`) — alasan `is_done` diganti `progress_pct`.** User minta progress lebih faktual: hari yang baru 90% dikerjain semestinya kontribusi 90% ke `actual_pct`, bukan 0% karena belum "Selesai" penuh. `actual_pct` di semua level berubah dari `100*count(is_done)/count(*)` jadi `AVG(progress_pct)` — hasilnya identik kalau semua nilai masih 0/100, jadi ini generalisasi murni bukan breaking change. Detail: `docs/decision-log/decision-log-day-entry-progress-pct-20260810.md`.

**Daily Task collapse + "sudah selesai" filter (2026-08-20) — kenapa ini state UI, bukan DB.** Awalnya bisa saja diasumsikan butuh kolom baru, tapi ini murni preferensi tampilan personal per browser, bukan data yang perlu di-share/di-audit — jadi disimpan `localStorage`, bukan backend.

Ditemukan user via screenshot. Fix & rule lengkap: `docs/decision-log/decision-log-dashboard-board-level-aggregation-20260810.md`.

**Gotcha/bug ketemu 2026-08-10 — section "Progress: actual vs expected (%)" + "Deadline terdekat" cuma nampilin board `status==='running'`, jadi board baru (0 Big Task) TIDAK PERNAH muncul di situ** (padahal sudah benar muncul di stat card/donut "Status project"). Pelajaran: kalau nambah section dashboard baru yang nge-list board, pikirkan dulu status mana yang relevan — jangan default ke "cuma yang running" tanpa alasan eksplisit.

**Dashboard: warna identitas board di chart (2026-08-20) — kenapa diganti dari label teks ke dot+legend.** `GroupedBarChart.svelte` awalnya render nama board sebagai `<text>` di bawah tiap bar (dipotong via `truncateName`) — begitu board makin banyak, nama tabrakan/gak kebaca (dikeluhkan user). Fix ikuti pola skill `dataviz`: warna identitas per board di-assign via HASH deterministik dari `boardId` (bukan index array), supaya board yang sama SELALU dapat warna sama walau di-filter/re-order (aturan "color follows the entity, never its rank").

## Auth

**Gotcha Svelte/SvelteKit (root layout gating) — PENTING, regresi dua kali.** Di `+layout.svelte`, `<slot/>` HARUS selalu dibungkus div yang sama, di posisi `{#if/else}` yang sama, baik untuk halaman login maupun sudah-login. Ketemu & diperbaiki di Fase 0 (wiring login), lalu REGRESI LAGI saat redesign visual (Fase "1.5") karena struktur `{:else if isLoginPage} <slot/> {:else} <div class="app">...<slot/></div>` ditulis ulang tanpa sadar itu pola yang sama. Begitu perubahan state auth (abis login) terjadi bersamaan navigasi route, `<slot/>` yang "pindah cabang" struktural bikin komponen halaman tujuan mount DUA KALI (fetch data dua kali). Root cause pasti belum jelas (dugaan interaksi `<svelte:component>` remount dengan `goto()` di tick yang sama), tapi fix-nya terbukti reprodusibel dua kali menghilangkan gejala.

## Frontend/Svelte gotchas

**PENTING — "retro" itu VISUAL doang, bukan wajib retro di semua interaksi (klarifikasi user, 2026-08-10).** Sempat 2 kali ke-drift ke arah "murni retro": (1) `.app` dikasih `max-width` fixed + gray desktop backdrop biar kelihatan kayak window ngambang — DITOLAK user (lihat gotcha layout di bawah); (2) semua boolean state dipaksa jadi tombol teks gonta-ganti label. Rule-nya: token warna/font/border/chrome tetap ikut retro theme, TAPI kalau ada pola interaksi MODERN yang lebih jelas buat user, pakai itu — jangan maksa niru semua widget Windows 9x lawas. Kalau ragu, tanya user, jangan asumsi sepihak.

**Gotcha layout: `.app` HARUS fluid, JANGAN dikasih `max-width` + `margin:auto`.** Dilaporkan user "My Weekly Plan berantakan" di monitor lebar (2026-08-10, sesi pertama) — waktu itu di-"fix" dengan `.app { max-width: 1280px; margin: 0 auto; }` + `body{background:#808080}` biar kelihatan kayak window retro ngambang. User COMPLAIN LAGI: itu bikin app kelihatan fixed-width, bukan visual-only retro. Fix final: `.app` fluid, root cause sparse-table di-fix DI TABEL-nya sendiri (`.weekplan-table { max-width: 900px; }`). Kalau tabel/section baru berantakan di monitor lebar, kasih `max-width` ke ELEMEN ITU SENDIRI, jangan pernah cap `.app`.

**Gotcha: `<input type="date">` dua-berdampingan di sidebar sempit (200px) overflow keluar container.** Input date native punya minimum rendered width intrinsik lebih lebar dari separuh 200px. Fix: `.inline-form-dates` dapat `flex-wrap: wrap; width: 100%;` + child dapat `flex: 1 1 100px; min-width: 0;`.

**Gotcha overlay/modal + a11y linter Svelte.** Div overlay dengan `on:click` untuk nutup modal selalu kena warning `a11y-click-events-have-key-events`/`a11y-no-static-element-interactions`. `role="presentation"` JUSTRU bikin warning muncul lagi (konflik dengan listener yang menetap di elemen itu). Solusi yang benar: `<svelte:window on:keydown={escHandler}/>` untuk Escape + svelte-ignore comments di overlay div DAN di `modal-box` inner div (kena rule berbeda karena `on:click|stopPropagation`).

**Gotcha: parent/child staleness setelah update anak.** Update di anak (mis. `DailyTaskPanel` toggle Day Entry) TIDAK otomatis me-refresh data parent (`BigTaskList`) — sempat bikin header/tombol sign-off basi (409 padahal progress sebenarnya 100%). Solusi: child `dispatch('updated')`, parent dengarkan via `on:updated={() => load({ silent: true })}` — bukan `on:updated={load}` polos (lihat gotcha `silent` di bawah).

**Gotcha: re-fetch setelah mutasi kecil terasa kayak "page refresh" walau SPA — root cause & fix pola `load({ silent })`.** Dilaporkan user 2026-08-10: ubah teks "Rencana" di Day Entry kerasa kayak submit HTML form biasa. Root cause BUKAN soal Svelte vs framework lain — murni bug pola loading state: `load()` toggle `loading = true` di SETIAP panggilan termasuk setelah mutasi kecil, dan template `{#if loading}...{:else}...{/if}` bikin SELURUH subtree unmount/remount tiap field disimpan (termasuk input yang lagi difokus). Lebih parah: `BigTaskList` ikut manggil `load()` saat dengar event `updated` dari anaknya. Fix: semua `load()` terima param `{ silent = false }`, semua caller pasca-mutasi pakai `load({ silent: true })`. Svelte keyed `{#each ... (item.id)}` otomatis update DOM in-place tanpa destroy elemen begitu `loading` tidak ditoggle.

**Gotcha Svelte (reactive assignment vs `bind:value`).** JANGAN pernah tulis `$: someVar = $store.field` untuk variabel yang juga dipakai `bind:value={someVar}` pada input yang sama — reactive statement re-run tiap invalidation cycle (termasuk yang dipicu `bind:value`-nya sendiri) dan menimpa balik yang baru diketik user. Ketemu di `settings/+page.svelte` (form ganti nama gak bisa disimpan sama sekali). Fix: init pakai `let someVar = $store.field` biasa (sekali saja, non-reaktif).

**Gotcha: response 200 tanpa body itu nyata, client harus defensif.** `bigtask.SignOff` awalnya cuma `w.WriteHeader(http.StatusOK)` padahal kontrak bilang harus balikin Big Task object — `res.json()` pada body kosong throw "Unexpected end of JSON input", bikin sign-off yang SUKSES di backend kelihatan GAGAL di frontend. Fix: `lib/api/client.ts` baca response sebagai teks dulu sebelum `JSON.parse`, sebagai jaring pengaman kedua (backend tetap harus diperbaiki tiap kali ketemu kasus begini).

**Gotcha: link download file TIDAK BOLEH pakai `<a href>` biasa.** Browser tidak menempelkan header custom (`Authorization: Bearer`) ke navigasi `<a href>` biasa (cuma cookie yang otomatis terkirim), dan access token kita in-memory bukan cookie — jadi `<a href="/api/v1/uploads/...">` akan SELALU 401. Fix: `downloadBlob(path)` fetch manual dengan header Authorization, hasil `Blob` dipakai bikin object URL sementara + `<a>` sintetis via JS.

**Gotcha Docker-dev + host build: EACCES saat `npm run build` di host.** Container `rndops-dev-frontend-1` jalan sebagai ROOT — begitu ada route baru, vite dev di dalamnya generate `.svelte-kit/types/.../$types.d.ts` sebagai root, dan `npm run build` di HOST gagal EACCES gak bisa overwrite file root itu. Bukan bug kode. Solusi tanpa sudo: build DI DALAM container (`docker exec rndops-dev-frontend-1 sh -c "cd /app && npm run build"`).

**Gotcha Svelte (keyed `{#each}` — jangan key pakai field yang bukan identitas unik).** `GroupedBarChart.svelte` sempat key pakai `d.name` (nama Big Task) — begitu ada DUA Big Task beda (id beda) yang kebetulan namanya sama (skenario nyata: dua board bisa sama-sama punya Big Task "Tahap Analisis"), Svelte CRASH "Cannot have duplicate keys in a keyed each". Fix: key pakai index array `(i)` untuk chart yang datanya cuma untuk render visual tanpa butuh stable identity lintas re-render.

**Gotcha ketemu 2026-08-10 (regresi lama) — default tab SettingsModal salah.** `let activeTab = canManage ? 'users' : 'theme'` dieksekusi SEBELUM reactive statement `$: canManage = ...` pernah jalan (plain `let` di atas jalan duluan) — `canManage` masih `undefined`, `activeTab` SELALU jatuh ke `'theme'` walau user admin/spv. Fix: default polos `let activeTab = 'users'` tanpa cek `canManage` di titik init; template sudah double-check `canManage` sendiri. Pola "`let x = someReactiveVar ? a : b`" di top-level JANGAN dipakai lagi.

**Gotcha flexbox: `.cr-item` (flex child dari `.cr-list` yang `display:flex`) butuh `min-width:0` eksplisit.** Tanpa itu browser biarkan item melebar ngikutin baris terpanjang alih-alih teksnya wrap (`min-width:auto` default flex item). Berlaku di mana pun ada teks panjang/dinamis di dalam flex container.

## Auth / session staleness

**Gotcha ketemu 2026-08-10 — sessionStorage cache di `authStore.init()` bikin field User baru (mis. `access_level`) kelihatan HILANG sampai user logout manual, walau DB & JWT-nya sudah benar.** `init()` DULU cek cache `sessionStorage` ("np_user") dulu, cuma fetch `GET /users/me` kalau cache kosong — user yang login sebelum field baru ditambahkan punya cache lama tanpa field itu, dan reload TIDAK memicu re-fetch (sessionStorage persist antar reload). Fitur `super_user` kelihatan gak jalan padahal backend benar, root cause murni cache browser basi. Diverifikasi cache ini TIDAK pernah mencegah flicker apapun (state `loading` tidak baca cached user). Fix: `init()` SEKARANG SELALU fetch fresh `GET /users/me`, `loadCachedUser` dihapus.

## Claude Chat Bridge

**Gotcha: `extractToken()` di `src/auth/setupTokenBridge.ts` BELUM divalidasi terhadap output CLI asli** — sengaja tidak dijalankan selama development (efek nyata: generate OAuth token baru). Verifikasi/sesuaikan regex parsing pas dites langsung pertama kali.

**Login OAuth Claude di-handle service sendiri, bukan `claude login` manual di server (2026-08-21) — kenapa & apa yang berubah.** User sempat login manual (`claude login`) langsung di server tempat `claude-chat-service` jalan, tapi service tetap melapor "OAuth access token has expired" — root cause: `claude login` (sesi interaktif biasa) BUKAN mekanisme yang dikonsumsi service untuk auth jangka panjang; `claude setup-token` (token OAuth ~1 tahun) adalah satu-satunya jalur yang didesain untuk proses headless seperti ini. Endpoint `POST /auth/setup-token` sudah ada dari awal tapi awalnya cuma one-shot spawn+wait tanpa cara ngirim input balik (proses PTY sering minta authorization code hasil approve browser di-paste balik ke terminal, gak ada local browser callback di environment headless/SSH). Diperbaiki jadi session-based + input channel: `runSetupToken` callback-based, balikin `SetupTokenHandle{sessionId, sendInput, kill}`; SSE kirim event `session` duluan, sesi PTY disimpan in-memory (`activeSetupSessions`), route baru `POST /auth/setup-token/{sessionId}/input` untuk kirim code di request terpisah.

**Gotcha Docker-dev host reachability — `claude-chat-service` dijalankan di HOST, bukan via docker-compose-nya sendiri (dev lokal).** Alasan: (a) service baca direktori project langsung dari filesystem — di host `CHAT_DEFAULT_CWD` langsung valid, di Docker harus mount path & cwd jadi `/workspaces/...` (gak match config); (b) auth OAuth — `claude` CLI di host sudah authenticated, Agent SDK pakai kredensial itu LANGSUNG tanpa `POST /auth/setup-token`. Backend (di Docker) reach service via `host.docker.internal:8091`. `CLAUDE_CHAT_SERVICE_URL` kosong/salah pointing bikin proxy default ke `localhost:8090` DI DALAM container backend = dirinya sendiri → 502 (gejala nyata terjadi saat container belum di-recreate abis nambah env var; fix: `docker compose -f docker-compose.dev.yml up -d --no-deps backend`).
