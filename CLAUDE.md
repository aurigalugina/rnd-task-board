## Living Memory — WAJIB DIBACA

File ini bukan dokumen statis sekali-tulis, tapi **living memory** — harus terus diperbarui seiring project berjalan. Setiap sesi Claude Code berikutnya:

- **Update file ini** kalau menemukan keputusan arsitektur baru, aturan bisnis baru, gotcha/jebakan yang baru ditemukan, atau asumsi lama di sini yang ternyata sudah berubah/salah.
- **Jangan biarkan basi.** Kalau kode sudah menyimpang dari yang tertulis di sini (misalnya modul baru sudah diimplementasi, atau pattern berubah), perbarui bagian terkait saat itu juga — jangan tunggu diminta.
- **Tulis ringkas, bukan naratif.** Tambahkan fakta + alasan singkat (kenapa keputusan itu diambil), bukan cerita panjang proses debugging.
- Kalau ragu apakah sesuatu layak masuk sini: masuk sini kalau itu hal yang **tidak bisa ditebak cuma dari baca kode** (keputusan arsitektur, alasan di balik pola tertentu, batasan yang harus dipatuhi) — bukan hal yang sudah jelas dari struktur file.

## Decision Log — wajib dicatat tiap final decision

Setiap kali sebuah keputusan sudah **final** (bukan lagi didiskusikan/dipertimbangkan — sudah disepakati untuk dijalankan), catat dulu ke decision log **sebelum** lanjut implementasi:

- Lokasi: `docs/decision-log/decision-log-[context]-YYYYMMDD.md`
- `[context]` = slug singkat kebab-case yang menjelaskan topik keputusan, mis. `kanban-state-machine`, `role-based-auth`, `sqlc-migration`.
- `YYYYMMDD` = tanggal keputusan difinalisasi.
- Satu file per keputusan/topik diskusi (bukan satu file besar yang terus ditambah) — supaya history tiap keputusan tetap terlacak per tanggal.
- Isi minimal: **konteks/masalah**, **keputusan yang diambil**, **alasan** (termasuk alternatif yang ditolak kalau relevan), dan **dampak/file yang terpengaruh**.
- Setelah decision log dibuat, kalau keputusan itu juga mengubah pola/arsitektur yang dipakai jangka panjang, sinkronkan ringkasannya ke bagian relevan di CLAUDE.md ini juga (lihat `Living Memory` di atas) — decision log mencatat kronologi "kenapa & kapan", CLAUDE.md mencatat state final "begini caranya sekarang".

## Testing — wajib sebelum task code dianggap selesai

Setiap task yang menyentuh logika kode (fitur baru, bug fix, refactor — bukan cuma dokumentasi/config) **wajib ada unit test-nya sebelum task itu dilaporkan selesai**, bukan ditunda ke sesi/fase testing terpisah nanti.

- **Backend (Go):** tambah/perbarui `_test.go` untuk logic yang disentuh — prioritaskan logika computed murni (`computeVerdict`, kalkulasi `actual_pct`/`expected_pct`, rollup mingguan, dsb) karena itu yang paling gampang salah diam-diam dan paling sering disebut sebagai prinsip tidak bisa ditawar di BRD. Jalankan `go test ./...` sampai hijau sebelum lapor selesai.
- **Frontend:** minimal `npm run check` tiap ubah `.svelte`/`.ts`. Kalau ada logic non-trivial yang ditambahkan (bukan cuma markup/styling — mis. logic di store, kalkulasi, parsing), tulis unit test-nya juga. Test runner: **vitest** (`npm run test`), sudah terpasang sejak Fase 1 — logic murni yang layak ditest biasanya diekstrak ke file `.ts` biasa di `lib/` (bukan ditinggal inline di `<script>` komponen), supaya bisa di-import & ditest tanpa render komponen. Contoh: `lib/dateRange.ts`, `lib/comments.ts`, `lib/dashboardStats.ts`.
- Fase 8 roadmap (lihat `docs/decision-log/decision-log-development-roadmap-20260808.md`) **sudah selesai** — audit menyeluruh logic computed murni yang lolos tanpa test dari fase-fase sebelumnya, ditambahkan sekaligus: `auth.RequireRole` (matching role, security-critical), `dailytask.isWeekend`/`parseDateRange`, `weeklyplan.parseWeekStart`, dan `dashboardStats.computeDashboardStats`/`truncateName` (diekstrak dari `routes/+page.svelte` khusus supaya testable). Kalau nemu logic computed murni baru yang belum ada test-nya, jangan tunggu "fase testing" lagi — langsung tambah saat itu juga (lihat aturan di atas).
- Task dengan perubahan yang murni tidak testable via unit test (mis. wiring UI yang divalidasi manual di browser, config) boleh cukup divalidasi manual — tapi kalau ada logic yang bisa diuji di dalamnya (mis. logic di dalam komponen/store), logic itu tetap wajib ditest.

## Dev Environment (Docker)

`docker-compose.dev.yml` (2026-08-10) — versi hot-reload dari `docker-compose.yml` (yang itu murni buat build/prod: multi-stage Dockerfile, output statis, nginx). Detail lengkap & alasan: `docs/decision-log/decision-log-docker-dev-compose-20260810.md`.

- Backend: `backend/Dockerfile.dev` pakai [`air`](https://github.com/air-verse/air) (watch `.go`, auto rebuild+restart), source di-bind-mount (`./backend:/app`), Go module cache & `tmp` build dir pakai NAMED VOLUME (bukan host dir langsung) — `tmp` tetap dibuat sebagai mountpoint kosong di host tiap kali stack ini nyala (harmless, sudah di `.gitignore`).
- Frontend: image `node:20-alpine` polos (gak perlu Dockerfile sendiri), `npm install && npm run dev -- --host --port 5173` tiap start, `node_modules` pakai named volume (biar gak ke-overwrite bind mount host & gak install ulang tiap restart).
- **Gotcha: `air@latest` butuh Go lebih baru dari base image `golang:1.22-alpine`.** `go install github.com/air-verse/air@latest` gagal ("requires go >= 1.26.0") kalau base image cuma punya go1.22. Fix: `ENV GOTOOLCHAIN=auto` sebelum `go install` di `Dockerfile.dev` — biar Go otomatis download toolchain lebih baru CUMA buat compile `air` (tool terpisah), tidak mengubah `go.mod` project (tetap `go 1.22`, tidak perlu upgrade base image `golang:1.22-alpine` yang dipakai buat build App-nya sendiri).
- **`vite.config.ts` proxy `/api` di-parameterize via `process.env.VITE_API_PROXY_TARGET`** (default tetap `http://localhost:8080` buat dev lokal biasa tanpa Docker — TIDAK ADA perubahan behavior kalau env var-nya gak di-set). Di `docker-compose.dev.yml`, frontend container set `VITE_API_PROXY_TARGET=http://backend:8080` (nama service di docker network) — kalau tetap hardcode `localhost:8080`, proxy dari dalam container frontend akan nyasar ke dirinya sendiri, bukan ke container backend.
- Port sama dengan versi build (`5432`/`8080`) — TIDAK bisa jalan bersamaan dengan `make up`, harus `make down` dulu.

## Arsitektur

Monolith modular, bukan microservices — satu binari Go, dipisah per domain secara logis via internal package, satu instance Postgres. Ini keputusan skala yang disengaja (lihat `04-architecture.md` §1); jangan usulkan pemisahan jadi banyak service.

**Alur request:** Nginx → build statis SvelteKit (adapter-static, tanpa SSR) untuk `/`, reverse-proxy ke backend Go/chi untuk `/api/*`.

**Pola modul backend** (`backend/internal/<domain>/handler.go`): tiap domain punya struct `Handler` yang membungkus `*pgxpool.Pool`, dibuat via `NewHandler(pool)`, method-nya langsung dipasang ke route chi di `cmd/api/main.go`. Tidak ada layer service/repository — handler query `pgx` langsung. Semua 10 modul yang didokumentasikan di `05-api-contract.md` (`board`, `bigtask`, `dailytask`, `user`, `comment`, `cheatsheet`, `upload`, `weeklyplan`, `reviewqueue`) sudah diimplementasi penuh (roadmap Fase 0–7 selesai) — kalau mau menambah modul baru di luar kontrak yang ada, ikuti pola yang sama (struktur file sama, gaya inline-SQL sama, bentuk struct request/response sama), dan pasang route baru ke grup `protected` di `main.go`.

**sqlc belum aktif.** Meskipun disebut di `04-architecture.md` sebagai pendekatan yang dituju, handler saat ini pakai query `pgx` mentah supaya scaffold ini bisa langsung dibangun tanpa langkah `sqlc generate`. `06-db-design.md` §5 mendokumentasikan pola query sqlc yang dituju sebagai referensi untuk migrasi nanti — jangan aktifkan tooling sqlc tanpa didiskusikan dulu, dan jangan asumsikan file `.sql` di `backend/db/queries/` sudah terpakai (folder itu masih kosong).

**Field yang dihitung saat baca (read-time) — jangan pernah disimpan sebagai kolom:** `actual_pct`, `expected_pct`, `verdict` (big task), `completion_rate`/`project_status` (board summary), `is_weekend` (day entry). Nilai-nilai ini bergantung pada waktu berjalan (`TODAY`) atau agregasi baris anak, dan wajib dihitung ulang tiap kali dibaca (lihat `04-architecture.md` §5.1, `06-db-design.md` §1). Ini keputusan sadar untuk menghindari kebutuhan cron job harian. Kalau menambah field turunan baru, ikuti pola ini, jangan disimpan permanen.

**Logika verdict** (`backend/internal/bigtask/handler.go: computeVerdict`): status `on_progress` bersifat netral berapa pun gap antara actual vs expected, sampai ada titik keputusan (sign-off, atau deadline lewat tanpa sign-off) — win/lose baru ditentukan di titik itu, bukan berdasarkan tertinggal jadwal di tengah jalan (BRD RULE-04/05/06).

**Sign-off** (`big_task_signoffs`): keberadaan baris = signed. Undo = hapus baris tersebut (bukan flag status). Sign-off ditolak dengan 409 kalau `actual_pct < 100` (BRD RULE-07).

**Generate Daily Task → Day Entry**: membuat Daily Task akan insert satu baris `day_entries` per tanggal kalender dalam rentang `[start_date, end_date]` inklusif, di dalam satu transaksi (SRS FR-DLY-01/02). `is_weekend` dihitung dari `entry_date` saat baca, tidak pernah disimpan.

**Auth**: JWT stateless untuk access token (HS256, env `JWT_SECRET`, expiry 2 jam) dikirim sebagai `Authorization: Bearer <token>` dari frontend. Refresh token JUGA JWT stateless terpisah (claim `typ:"refresh"`, expiry 7 hari), dikirim via cookie httpOnly (`Path=/api/v1/auth`, `SameSite=Lax`, `Secure` aktif kalau `APP_ENV=production`) — tidak ada tabel session/refresh-token di DB, sesuai `04-architecture.md` §6. Detail & alasan lengkap: `docs/decision-log/decision-log-auth-rbac-implementation-20260808.md`.

`auth.RequireAuth` (`backend/internal/auth/auth.go`) memvalidasi access token dan menyisipkan `userID` + `roles` (dari claim JWT, bukan query ulang ke DB) ke context. `auth.RequireRole("spv", ...)` adalah middleware terpisah yang harus dipasang SETELAH `RequireAuth` di chain — cek contoh pemasangannya di `main.go` untuk endpoint sign-off/undo-signoff. Role di access token statis selama masa berlaku token (maks 2 jam) — kalau role user diubah di tengah jalan, perubahan baru kepakai setelah access token expire dan di-refresh ulang (`POST /auth/refresh` query roles fresh dari DB tiap kali dipanggil).

Frontend: `frontend/src/lib/stores/authStore.ts` — access token disimpan in-memory saja (lewat `setAccessToken` di `client.ts`, bukan localStorage), sesi di-restore saat app dimuat lewat silent refresh (`POST /auth/refresh`, mengandalkan cookie httpOnly). Info user non-sensitif (nama/inisial/role/org_team) di-cache di `sessionStorage` cuma buat tampilan, bukan buat auth. Redirect ke `/login` ditangani reactive statement di `+layout.svelte`; redirect balik ke `/` setelah login dipanggil eksplisit di `login/+page.svelte`.

**Gotcha Svelte/SvelteKit (root layout gating) — PENTING, sempat regresi sekali:** di `+layout.svelte`, `<slot/>` HARUS selalu dibungkus div yang sama, di posisi {#if/else} yang sama, baik untuk state "halaman login" maupun "sudah login" — cuma `class` pada div pembungkus dan sibling-nya (titlebar/topbar) yang boleh toggle via `{#if}` terpisah. JANGAN taruh `<slot/>` sebagai satu-satunya isi cabang `{#if isLoginPage}` yang berbeda dari cabang `{:else}` tempat app-shell dirender — begitu perubahan state auth (abis login) terjadi bersamaan dengan navigasi route, `<slot/>` yang "pindah cabang" struktural bikin komponen halaman tujuan sempat mount DUA KALI (fetch data dua kali). Ketemu & diperbaiki di Fase 0 (wiring halaman login), lalu **regresi lagi** waktu redesign visual (Fase "1.5", adopsi mockup retro) karena struktur `{:else if isLoginPage} <slot/> {:else} <div class="app">...<slot/></div>` yang sama persis ditulis ulang tanpa sadar itu pola yang sama. Bentuk final yang aman ada di `routes/+layout.svelte` sekarang: satu `<div class="app" class:login-mode={isLoginPage}>` yang selalu ada, isinya `{#if !isLoginPage}` titlebar+topbar (tidak membungkus slot) lalu `<div class={isLoginPage ? 'login-content' : 'content'}><slot/></div>` — div pembungkus slot ini SELALU ada di posisi yang sama, cuma class-nya yang beda. Root cause pasti belum jelas (dugaan interaksi `<svelte:component>` remount SvelteKit dengan navigasi `goto()` di tick yang sama), tapi fix ini terbukti reprodusibel dua kali menghilangkan gejalanya — kalau nanti nambah state baru yang mengubah tampilan sekitar `<slot/>`, TIRU pola "div pembungkus tetap ada, cuma class/sibling yang toggle", jangan pola "cabang if terpisah yang isinya cuma slot".

**Role** bersifat many-to-many via `user_roles` (bukan kolom tunggal di `users`) — kode role: `spv`, `sa`, `dev`, `qa`, `admin` (di-seed di `0001_create_users_roles.up.sql`).

**Migration**: file SQL bernomor biasa di `backend/db/migrations/` (`NNNN_deskripsi.up.sql` / `.down.sql`), dijalankan via image Docker `migrate/migrate` (tidak perlu install CLI lokal) — lihat Makefile.

**Frontend — struktur halaman kerja (Fase 1):** `routes/+page.svelte` (Dashboard) menampilkan matriks summary per board (`GET /boards/{id}/summary`) buat cek cepat ala Vision Product §7 ("SPV jawab progress tim <1 menit"). `routes/boards/+page.svelte` adalah halaman kerja penuh: tab pilih board (state di URL via `?board=<id>`) → `lib/components/BigTaskList.svelte` (list + create Big Task, tombol sign-off/undo-signoff, hanya tampil kalau role `spv` ada di `$auth.user.roles`) → expand baris → `lib/components/DailyTaskPanel.svelte` (list + create Daily Task, tabel Day Entry inline-editable, PIC picker dari `GET /users/assignable`). `lib/types.ts` isinya bentuk response API (jangan hitung ulang field turunan di sini, selalu dari server). `lib/dateRange.ts` (+ `.test.ts`) adalah preview murni rentang tanggal buat form Daily Task, mencerminkan logika inklusif backend (SRS FR-DLY-01/02) — kalau backend-nya berubah, sinkronkan ini juga.

**Frontend — Users & Settings (Fase 2):** endpoint backend (`GET/POST /users`, `GET/PATCH /users/me`, `GET /users/assignable`, `GET /roles`) — lihat modul `user`. `authStore.init()` fallback ke `GET /users/me` kalau cache `sessionStorage` kosong; `auth.refreshUser()` dipanggil setelah `PATCH /users/me` sukses supaya topbar dkk ikut update. Detail keputusan bentuk endpoint (password wajib di `POST /users`, `GET /users/me` baru, `current_password` wajib buat ganti password, `GET /users/assignable` terpisah dari `GET /users`): `docs/decision-log/decision-log-users-api-gaps-20260809.md` dan `docs/decision-log/decision-log-pic-assignment-endpoint-20260809.md`. **UI-nya (My Profile / Settings) pindah jadi modal** — lihat bagian Design System di bawah, `routes/settings` dan `routes/users` (halaman) sudah dihapus.

Kalau butuh chart baru yang jauh lebih kompleks dari donut/grouped-bar, itu baru alasan valid buat evaluasi ulang keputusan ini.

**Dashboard lintas board, POV per BOARD (=project) bukan per Big Task.** Diagregasi di CLIENT dari `GET /boards` + `GET /boards/{id}/big-tasks` tiap board (di-`Promise.all`), TIDAK ada endpoint backend baru buat ini. Skala kecil (NFR-03) bikin ini aman performa. Sempat SALAH sekali (regresi ditemukan user via screenshot 2026-08-10): stat card/donut/chart/tabel sempat menghitung per Big Task langsung, padahal Dashboard-nya dimaksudkan buat lihat progress per **project** (Vision Product §7) — board = project. Fix & rule lengkap: `docs/decision-log/decision-log-dashboard-board-level-aggregation-20260810.md`. Agregasi 2 tingkat di `lib/dashboardStats.ts`: `aggregateBoards()` (Big Task → satu baris `BoardAgg` per board) lalu `computeDashboardStats()` (BoardAgg[] → statistik portfolio). Rule status board: **all-or-nothing per bucket, default "running" kalau campuran** — `done` HANYA kalau SEMUA Big Task signed (match `project_status` di `GET /boards/{id}/summary`), `hold` HANYA kalau SEMUA on_hold, `not_started` HANYA kalau SEMUA 0%/board belum punya Big Task; campuran apapun → `running`. Rule verdict board: **asimetris** dengan status (ikut filosofi netral-sampai-keputusan yang sama dengan verdict Big Task individual) — `lose` kalau ADA MINIMAL SATU Big Task lose (sinyal negatif tidak boleh ketutupan rata-rata, walau status board-nya `done`), `won` HANYA kalau status `done` DAN tidak ada lose sama sekali. Progress chart pakai rata-rata `actual_pct`/`expected_pct` semua Big Task di board; "Deadline terdekat" pakai `min(days_left)` Big Task yang belum signed. Kalau nambah metrik dashboard baru, agregasi dulu ke level board pakai pola ini, JANGAN render satu baris per Big Task langsung. "Tim" grid di Dashboard cuma nampilin identitas+role dari `GET /users/assignable` — TIDAK ada hitungan "task aktif"/"belum direview" per orang (butuh cross-reference Daily Task lintas board yang mahal utk N+1 fetch, dan "belum direview" butuh Review Queue yang belum dibangun/Fase 7) — jangan tambah balik tanpa endpoint agregat backend yang proper.

**My Profile & Settings jadi modal**, bukan route halaman (`lib/components/ProfileModal.svelte`, `lib/components/SettingsModal.svelte`), dipanggil dari dropdown avatar user di topbar (`+layout.svelte`) — sesuai pola asli mockup (bukan cuma warnanya yang diikuti, pola interaksinya juga). `SettingsModal` punya 2 tab: "Manajemen user" (cuma render kalau admin/spv) dan "Tema aplikasi" (semua role).

**Gotcha layout: `.app` wajib punya `max-width` (1280px), jangan biarkan stretch full-viewport.** Sempat dilaporkan user "My Weekly Plan berantakan" di monitor lebar — root cause bukan bug logic, tapi `.app` polos `width:100%` tanpa `max-width`, jadi tabel sparse (kolom sedikit, banyak whitespace) melebar sampai ujung monitor ultra-wide dan kelihatan berantakan. Fix: `.app { max-width: 1280px; margin: 0 auto; }`. Kalau nambah halaman/tabel baru yang datanya sedikit kolom, jangan taruh `width:100%` tanpa cap — akan kena masalah yang sama di monitor lebar.

**Gotcha: `<input type="date">` dua-berdampingan di sidebar sempit (200px, `.bigtask-list`) overflow keluar container.** Input date native punya minimum rendered width intrinsik yang lebih lebar dari separuh 200px, jadi form "Tambah big task" (`BigTaskList.svelte`, pakai `.inline-form-dates`) date picker-nya "keluar" dari sidebar kalau cuma `display:flex` polos tanpa wrap. Fix: `.inline-form-dates` dapat `flex-wrap: wrap; width: 100%;` + child (`.inline-input`, `input[type='date']`, `> label`) dapat `flex: 1 1 100px; min-width: 0;` — biar shrink dan jatuh ke baris baru kalau sempit, bukan overflow. Class ini dipakai bareng oleh `BigTaskList.svelte` (tanpa label wrapper) dan `DailyTaskPanel.svelte` (dengan `<label>` wrapper) — kalau nambah form tanggal baru di kolom sempit, pakai class ini, jangan bikin flex row date input baru dari nol.

**Gotcha overlay/modal + a11y linter Svelte:** div overlay yang `on:click` buat nutup modal (klik backdrop) akan selalu kena warning `a11y-click-events-have-key-events` dan `a11y-no-static-element-interactions`/`a11y-no-noninteractive-element-interactions` — solusinya bukan `role="presentation"` (itu malah bikin div-nya dianggap non-interactive dan warning JUSTRU muncul lagi di elemen yang sama, konflik sama listener yang menetap di elemen itu), tapi kombinasi `<svelte:window on:keydown={escHandler}/>` buat Escape + `<!-- svelte-ignore a11y-click-events-have-key-events -->` + `<!-- svelte-ignore a11y-no-static-element-interactions -->` di atas div overlay, DAN `<!-- svelte-ignore a11y-no-noninteractive-element-interactions -->` tambahan di div `modal-box` bagian dalam yang punya `on:click|stopPropagation` (kena rule berbeda dari overlay-nya). Lihat `ProfileModal.svelte`/`SettingsModal.svelte` buat contoh lengkapnya.

**Gotcha: parent/child staleness setelah update anak.** `BigTaskList` fetch sendiri data agregat Big Task (actual_pct/verdict/eligibility sign-off); `DailyTaskPanel` (anak, di-render saat expand) fetch data Daily Task-nya sendiri. Update di anak (toggle Day Entry, create Daily Task) TIDAK otomatis me-refresh data parent — kalau tidak ditangani, header Big Task & tombol sign-off jadi basi (sempat 409 padahal progress sebenarnya sudah 100%, ketemu & diverifikasi langsung waktu wiring Fase 1). Solusi yang dipakai: `DailyTaskPanel` `dispatch('updated')` (Svelte `createEventDispatcher`) tiap kali sukses create/update, parent dengerin via `on:updated={load}`. Kalau nambah level nesting baru (mis. komentar di bawah Daily Task), pola yang sama harus diikuti — jangan asumsikan re-fetch otomatis lintas komponen.

**Gotcha Svelte (reactive assignment vs `bind:value`):** JANGAN pernah tulis `$: someVar = $store.field` untuk variabel yang juga dipakai di `bind:value={someVar}` pada input yang sama. Reactive statement itu re-run tiap invalidation cycle (termasuk yang dipicu oleh `bind:value`-nya sendiri) dan langsung menimpa balik apa pun yang baru diketik user — ketemu & diverifikasi di `settings/+page.svelte` (form ganti nama sempat tidak bisa disimpan sama sekali karena reactive statement terus me-reset input ke nilai lama). Fix: init pakai `let someVar = $store.field` biasa (sekali saja, non-reaktif), bukan `$:`. Pola ini berlaku di mana pun ada form yang initial value-nya dari store/props tapi field-nya user-editable.

**Gotcha: response 200 tanpa body itu nyata, client harus defensif.** `bigtask.SignOff` awalnya cuma `w.WriteHeader(http.StatusOK)` padahal `05-api-contract.md` §4 bilang harus balikin Big Task object — `res.json()` di frontend pada body kosong throw "Unexpected end of JSON input", bikin sign-off yang SUKSES di backend kelihatan GAGAL di frontend (silent contract violation, ketemu pas wiring Fase 1, sudah diperbaiki: `bigtask.loadBigTask` helper dipakai buat balikin object lengkap). `lib/api/client.ts` sekarang baca response sebagai teks dulu sebelum `JSON.parse` (bukan langsung `res.json()`), biar deviasi kontrak serupa di endpoint lain nggak bikin gagal-diam-diam — tapi backend tetap harus diperbaiki juga tiap kali ketemu kasus begini, defensive parsing ini cuma jaring pengaman kedua.

**Comments (Fase 3):** `backend/internal/comment/handler.go` — `GET /big-tasks/{id}/comments?scope=all|general|{daily_task_id}` dan `POST` (author_id selalu dari JWT, FR-CMT-05). Frontend: `lib/components/CommentSection.svelte`, dirender di `BigTaskList.svelte` setelah `DailyTaskPanel` untuk Big Task yang aktif. `DailyTaskPanel` yang punya daftar Daily Task asli (buat label scope filter) — dikirim ke atas via event `tasksLoaded` (bukan CommentSection fetch sendiri), dan tombol "💬 Komentar" per Daily Task dispatch `jumpToComment` yang diteruskan `BigTaskList` sebagai prop `jumpScope`/`jumpToken` ke `CommentSection` (pola sama seperti `jumpScope`/`jumpToken` di `ProjectView` mockup — `jumpToken` di-increment tiap klik supaya reactive block ke-trigger walau `jumpScope`-nya sama seperti klik sebelumnya).

**Render komentar wajib lewat `lib/comments.ts` (`renderCommentHtml`), jangan `{@html}` body mentah.** Body komentar itu user input, di-escape HTML dulu baru mention (`@Nama` yang match `display_name` assignable user) dibungkus `<span class="mention-tag">` — escape SELALU jalan duluan sebelum wrap mention, urutan ini yang bikin aman dari XSS (kalau dibalik, span yang disisipkan bisa ke-escape juga atau body-nya keburu jadi vector). Ada unit test di `comments.test.ts` termasuk kasus body berisi tag HTML.

**`bigtask.computeExpectedPct`** (fungsi murni, ada test-nya) dipakai bareng oleh `ListByBoard` dan `loadBigTask` — kalau nambah endpoint baru yang butuh bentuk Big Task lengkap (mis. modul lain yang merujuk balik ke Big Task), pakai `loadBigTask`/`computeExpectedPct`, jangan copy-paste query+kalkulasinya lagi.

**Cheat Sheet & Upload (Fase 4):** `backend/internal/cheatsheet/` — CRUD referensi board (`file`/`url`/`note`), scope-nya BOARD bukan Big Task (beda dari comments). `backend/internal/upload/` — modul terpisah, `POST /uploads` (multipart, field `file`) simpan ke disk lokal (`UPLOAD_DIR`, default `/app/uploads`, di-mount sebagai docker volume `uploads` — **wajib ada volume-nya**, tanpa itu file hilang tiap restart container) dengan nama `<uuid>_<nama-asli-disanitasi>` (cegah collision & path traversal), dan `GET /uploads/{filename}` buat ambil lagi. Endpoint `GET /uploads/{filename}` tidak ada di draft awal kontrak — ditambahkan karena tanpa itu upload tidak bisa dipakai lagi (lihat `docs/decision-log/decision-log-file-upload-storage-20260809.md`).

**Gotcha: link download file TIDAK BOLEH pakai `<a href>` biasa.** Semua endpoint butuh `Authorization: Bearer <token>`, tapi browser tidak menempelkan header custom ke navigasi `<a href>` biasa (cuma cookie yang otomatis terkirim) — access token kita disimpan in-memory, bukan cookie, jadi `<a href="/api/v1/uploads/...">` akan SELALU 401 di real usage. Fix: `lib/api/client.ts` punya `downloadBlob(path)` yang fetch manual dengan header Authorization lalu dikembalikan sebagai `Blob`; caller (`CheatSheetSection.svelte`) bikin object URL sementara dan trigger `<a>` sintetis via JS buat memicu download beneran, nama file asli (`originalFilename()`, strip prefix UUID) dipakai sebagai `download` attribute. Pola ini WAJIB diikuti untuk resource lain yang butuh auth dan didownload langsung oleh browser (bukan di-fetch lalu ditampilkan sebagai JSON).

**Frontend Cheat Sheet**: `lib/components/CheatSheetSection.svelte`, dirender di `BigTaskList.svelte` di ATAS `project-layout` (scope board, tampil sekali per board terlepas Big Task mana yang aktif — beda dari `CommentSection` yang di dalam `bigtask-detail`). Upload pakai `api.upload()` (helper baru di `client.ts`, `FormData` sebagai body, TIDAK boleh set `Content-Type` manual — biarkan browser yang isi header multipart boundary-nya sendiri) sebelum `POST /boards/{id}/cheat-sheet` dengan `value` hasil upload.

**Clone-as-review (Fase 5):** `dailytask.CloneReview` — `POST /daily-tasks/{id}/clone-review` body `{role_tag: "SPV"|"QA", start_date, end_date}`, bikin Daily Task baru beneran di server (BUKAN cuma prefill form seperti demo di mockup — mockup itu murni frontend tanpa backend asli, jadi pola interaksinya di titik ini TIDAK diikuti, kontrak API yang jadi rujukan). Judul otomatis `"[Review {role_tag}] {judul asal}"`, PIC default = user pertama (urut `display_name` ASC) dengan role `spv`/`qa` — ditolak 400 kalau tidak ada user dengan role itu (lihat `docs/decision-log/decision-log-clone-review-20260809.md`). **`dailytask.loadDailyTask`/`insertDailyTaskWithDays`** (helper, pola sama seperti `bigtask.loadBigTask`) dipakai bareng oleh `Create` dan `CloneReview` — kalau nambah cara baru bikin Daily Task, pakai helper ini, jangan copy-paste query insert+day-entries-loop lagi. **Gotcha Svelte (keyed `{#each}` — JANGAN key pakai field yang bukan identitas unik, mis. `.name`):** `GroupedBarChart.svelte` sempat key pakai `d.name` (nama Big Task) — begitu ada DUA Big Task beda (id beda) yang kebetulan namanya sama (skenario nyata, bukan cuma edge case: dua board bisa sama-sama punya Big Task "Tahap Analisis"), Svelte CRASH runtime dengan "Cannot have duplicate keys in a keyed each". Ketemu & diverifikasi langsung waktu testing Fase 7 (dua board test dengan nama sama). Fix: key pakai index array (`(i)`) untuk chart yang datanya cuma buat render visual tanpa butuh stable identity lintas re-render — `DonutChart.svelte` ikut diubah ke pola yang sama untuk jaga-jaga meskipun datanya saat ini selalu kategori tetap (aman). Kalau nambah `{#each}` baru yang keyed, SELALU pastikan key-nya benar-benar unik (id dari backend), jangan pernah pakai display text (nama, judul, label) sebagai key.

## Jangan lakukan

- Jangan simpan `verdict`, `expected_pct`, `actual_pct`, `completion_rate`, atau `is_weekend` sebagai kolom tabel — wajib tetap computed-at-read (lihat penjelasan di atas).
- Jangan tambahkan kolom `role` tunggal di `users` — role itu many-to-many via `user_roles`.
- Jangan ganti auth ke cookie/session — ini API stateless Bearer-JWT by design.
- Jangan tambahkan layer abstraksi service/repository di handler backend — modul yang sudah ada query `pgx` langsung, modul baru harus ikut pola itu, jangan bikin pola baru.
- Jangan hapus `preprocess: vitePreprocess()` di `frontend/svelte.config.js` — tanpa itu `npm run build` gagal total begitu ada sintaks TypeScript (`type X = ...`, `as Y`) di dalam `<script lang="ts">` manapun (sempat kejadian, baru ketahuan Fase 0 karena belum pernah ada yang coba build).
- Jangan taruh `<slot/>` root layout di cabang `{#if}` terpisah per state auth — lihat gotcha di bagian Auth di atas.
- Jangan bikin halaman baru dengan styling ad-hoc (warna/spacing sendiri) — pakai token & class di `app.css` (lihat bagian Design System). Semua halaman yang sudah ada sudah di-re-skin mengikuti `docs/rnd-ops-mockup_3.jsx`, jangan mundur ke gaya polos lagi.
- Jangan tambah library chart (Recharts/Chart.js/dst) — chart yang dibutuhkan (donut, grouped bar) sudah di-cover `DonutChart.svelte`/`GroupedBarChart.svelte` custom SVG. Lihat decision log kalau kebutuhannya berubah jauh lebih kompleks.
- Jangan bikin ulang halaman/route buat "My Profile" atau "Settings" — itu sudah jadi modal (`ProfileModal.svelte`/`SettingsModal.svelte`) dipanggil dari dropdown user di topbar, bukan route SvelteKit.
